# Exploration: print-bridge-remoto

- Change: `print-bridge-remoto`
- Date: 2026-09-19
- Baseline: `origin/main` @ `5864c94` (v1.0.101). The `MOS-05` worktree is 31 commits behind and 6 commits ahead of main; none of its unique commits touch printing files, so all evidence below cites `origin/main`. **Apply MUST rebase onto `origin/main` before implementation.**

## Problem

A thermal printer hangs off the local Mac (`print-agent`). Devices on the same Wi-Fi (phone, another computer) cannot print: the app always targets `http://127.0.0.1:17890`, which on those devices is themselves, and the HTTPS→HTTP LAN fetch is blocked as mixed content. The Mac itself prints fine.

## Current State

### Printing pipeline

- The SPA prints by building ESC/POS bytes in the browser (`src/lib/printing/tickets.js`) and POSTing base64 to the local agent (`src/lib/printing/agent.js:252-285`, `imprimirDirecto` → `POST /print`, 5 s timeout).
- Agent base URL is a constant `http://127.0.0.1:17890` (`src/lib/printing/agent.js:16`) resolved per tenant/bridge in `configImpresora()` (`agent.js:146-164`). `URL_AGENTE` is also the placeholder for bridge URLs (`src/lib/printing/puentes.js:5`).
- The agent is an HTTP server on `0.0.0.0:17890` with a shared token (`print-agent/server.mjs:82,325`; token generated at `print-agent/config.mjs:21`), LAN (raw TCP 9100) plus CUPS/USB transports (`print-agent/transportes.mjs`), and a persistent local queue/history (`print-agent/cola.mjs`).
- Agent API surface: `/health`, `/jobs`, `/jobs/:id`, `/jobs/confirm`, `/jobs/retry`, `/jobs/clear`, `/historial`, `/print`, `/config`, `/diagnostico`, `/red/agregar` (`server.mjs:158-305`).
- Printer config, bridge list and bridge tokens live in `localStorage` per tenant **and per device** (`agent.js:26-31,88-97,128-132`; `puentes.js:12-17`). No printer data exists in the backend: no print model in `backend/prisma/schema.prisma` and no print routes under `backend/app/api`.
- "Confirmar en papel" (test tickets only): the browser generates a 4-digit `validacion` plus a 1-digit secret `sufijo` (`tickets.js:197-200,233-235`), the suffix is embedded in the ticket bytes, the agent stores it in history and validates it locally (`cola.mjs:155-166`, `server.mjs:202-215`) via a manual action in the UI (`Impresoras.jsx:637-648`). The app never echoes the suffix back; only the operator reading paper can confirm.
- Local fallback: `printHtml` (hidden iframe, `src/utils/printHtml.js:4-31`) via a **manual** action — `imprimirTicketOFallback` never auto-opens the dialog to avoid duplicate tickets (`agent.js:297-316`).
- Multi-bridge already exists: each printer can be bound to a bridge and the app syncs LAN allow-lists to the agent (`agent.js:237-248`, `Impresoras.jsx:758-810`). Configuration UI still shows the bridge address read-only (`Impresoras.jsx:1077-1079`).
- Presence is the repo's polling precedent: SPA heartbeat every 30 s (`src/hooks/usePresence.js:34`), backend table + idempotent migration (`backend/lib/presence.ts`, `backend/prisma/migrations/20261012000000_presence/migration.sql`). No WebSocket/SSE anywhere; root `package.json` has no `ws`/socket dependency.
- Backend auth patterns: cookie/Bearer sessions with SHA-256 `tokenHash` at rest (`backend/lib/auth.ts:192-205,354-374`), tenant-scoped queries via `requireSession`, audit through `auditLog` (`schema.prisma:1300-1314`), and a scheduler-only Bearer token pattern using `timingSafeEqual` (`backend/app/api/internal/email-outbox/route.ts:5-12`).
- The SPA talks to the API over HTTPS with cookies (`src/lib/api/client.js:7-10,70-82`; `VITE_API_URL=https://api.moboss.online`). The bridge agent would talk to the same host with Node 20 global `fetch` (no CORS/mixed-content involved).
- Distribution: `print-agent/install-macos.sh:27` copies files from the cloned repo (`cp "$ORIGEN/..."`), so it fails when run from a machine without the repo; the token is printed at the end (`install-macos.sh:122-125`).

### Verified facts that need a small correction

- Fact 8 said the secret number is generated by the agent: actually it is generated **in the browser** and only validated/stored by the agent (`tickets.js:197-200`, `cola.mjs:155-166`). This matters for the new flow (see Option E).
- Facts 1-7 hold in `origin/main`; main added the suffix validator, CUPS rename (`usb:`→`cups:`) and multi-bridge since the worktree snapshot.

## Hard Constraints

1. **Mixed content**: the SPA is HTTPS; `http://<LAN-IP>:17890` is blocked by the browser on non-local devices. Only `http://127.0.0.1` / `localhost` is exempt. A bridge must be reached server-side (outbound from the agent) or through TLS.
2. **Per-device storage**: `localStorage` does not sync across devices (`agent.js:31`). Anything the phone must know has to come from the backend.
3. **Local flow compatibility**: the Mac's fast path (`127.0.0.1`) and the manual `printHtml` fallback must keep working; `imprimirTicketOFallback` must not start auto-opening print dialogs (duplicate risk, `agent.js:293-307`).
4. **Honest states**: `aceptado` (transport accepted) ≠ `confirmado` (paper seen); `incierto` must never auto-retry (`cola.mjs:6-14,78-93`). The server-side queue must preserve this.
5. **Offline behavior**: the bridge may lose internet; claimed jobs must survive and report later, and remote jobs must not be lost server-side.
6. **Security**: bridge credential must be a per-tenant secret, hashed at rest (pattern: `auth.ts:192-204`), revocable and TLS-only; `/print` payloads carry customer PII inside ESC/POS bytes, so payload retention and access must be explicit.
7. **No duplicate prints**: claim/lease + idempotency on the server; `incierto` requires manual action.

## Options and Tradeoffs

### (a) Transport for the outbound connection

| Approach | Pros | Cons | Effort |
|---|---|---|---|
| **Short polling (~2 s)** | Matches repo precedent (presence 30 s); plain `fetch`; survives proxies/redeploys; trivial to reason about; no new deps | Up to ~2 s latency; N bridges × 30 req/min | Low |
| Long-poll | Lower latency and fewer requests | Holds HTTP+DB connections; proxy/timeout/abort edge cases; needs careful shutdown on redeploy | Medium |
| WebSocket/SSE | Real-time push | No WS/SSE in repo; needs persistent server/extra service; more moving parts for a 2 s problem | High |

**Recommendation: short polling** with per-bridge interval (2 s when online, exponential backoff to ~15-30 s on errors) and a lease on claims. Revisit long-poll only if the latency budget says so.

### (b) Where printer config lives — **PRODUCT DECISION PENDING**

| Approach | Pros | Cons |
|---|---|---|
| A. Keep `localStorage`, bridge stays the authority | No schema/API work; local flow untouched | Every device configures printers by hand; bridge allow-list only syncs when a device opens Impresoras (`Impresoras.jsx:107-111`); phone has no printer to choose; defeats the cross-device goal |
| B. Backend is source of truth per company | One configuration for all devices; bridge can sync its allow-list without an open browser; admin-only edits; enables remote queue tied to printer IDs | New models/migration/API; offline reads need a localStorage cache; one-time import from existing localStorage config; multi-bridge/branch semantics must stay bounded |

**Recommendation: B, with `localStorage` demoted to an offline cache** — the bridge must learn its printers and allow-list even when no browser is open on the Mac, and the phone cannot be configured per device. This is flagged as the pending product decision because it changes who edits printers (any device vs the bridge Mac) and requires a data migration UX.

### (c) Local flow and `printHtml` fallback

- Keep **local-first** on the bridge Mac: if `127.0.0.1:17890` responds, print locally (fast, offline, no server round-trip).
- Other devices enqueue remotely through the API; the bridge claims the job and prints.
- Never both: pick one path per job (server records the path actually used).
- Keep `printHtml` as the last, **manual** fallback (`imprimirConDialogo`), and keep "aceptado vs confirmado en papel" semantics in the server job states. Do not auto-open the dialog after a remote enqueue, to avoid duplicates.

### (d) Installer/distribution without a repo

| Approach | Pros | Cons | Effort |
|---|---|---|---|
| **Backend-served versioned tarball + one-liner** (`curl -fsSL https://api.moboss.online/print-agent/install.sh \| bash`) | No GitHub/repo needed; versions pinned to the backend; checksum verifiable; works from any Mac | Needs a public bootstrap endpoint and versioned artifact storage; `curl \| bash` review concerns | Medium |
| GitHub release tarball | Standard, free hosting | Requires GitHub network access and repo knowledge; version not tied to backend | Low-Med |
| npm package (`npx`) | Versioning/auth for free | Node already required; publish pipeline; still needs bridge token provisioning | Medium |
| Signed/notarized `.pkg` | Best UX, no Terminal | Codesign/notarization tooling, Apple account, slowest iteration | High |

**Recommendation: backend-served tarball + one-liner installer**, with checksum and a pairing step (below). Keep the repo path working for development. A signed `.pkg` is an explicit non-goal for now.

### (e) Secret number generation and validation

Today: browser generates `validacion` + 1-digit `sufijo`, bytes embed it, agent stores and validates (`tickets.js:197-235`, `cola.mjs:155-166`).

| Approach | Pros | Cons |
|---|---|---|
| A. Keep generation in the client; move **validation/storage to the backend** | Minimal change; bytes already contain the secret; history becomes company-wide | A malicious client knows the suffix (same as today); backend must never expose it via GET |
| B. Backend generates the suffix; client fetches it before building the ticket | Server owns the secret | Extra round trip before every ticket; awkward because the payload is assembled in the browser; sales tickets have no suffix today |
| C. Bridge appends the suffix to the payload | Secret never leaves server/bridge | Bridge would parse/modify ESC/POS bytes (cut/QR commands), risky and printer-specific |

**Recommendation: A.** Keep client generation, store `suffix` server-side on the job, validate only through `POST /api/print/jobs/{id}/confirm`, never return it in job listings. Applies to test tickets; sales tickets keep no suffix. Document that the secret proves operator honesty, not cryptographic security.

## Risks

- **Duplicate tickets** if a polled job is retried after an uncertain send; mitigate with leases, idempotency keys and "never auto-retry incierto".
- **Config divergence** while both localStorage and backend exist (dual-write windows, migration mistakes) if decision (b) goes to backend.
- **Bridge offline/online flapping** leaving jobs claimed forever; lease expiry + requeue policy needed.
- **Backend dependency** for remote devices: if the API is down they can only use the manual dialog; the Mac keeps its local fast path.
- **PII retention**: ESC/POS payloads contain customer data; without a retention rule the new tables become a shadow copy of sales.
- **Branch hygiene**: `MOS-05` must rebase before apply; 6 unrelated commits could conflict.
- **Scope creep**: per-branch multi-bridge routing, native app, WS and signed installers are out of scope.

## Open Questions

**Require user decision (block proposal/design):**

1. (b) Printer configuration: backend source of truth per company, or keep `localStorage` per device? Recommendation: backend + cache.
2. (d) Distribution: is a `curl | bash` installer served by `api.moboss.online` acceptable, or is a signed `.pkg` required?
3. (e) Are we comfortable with the suffix being generated client-side and only validated server-side?
4. Retention/privacy: how long do we keep job payload bytes and metadata, and who may read history?
5. Latency budget: is ~2 s (short polling) acceptable, or must it feel instant (long-poll/SSE)?
6. Local vs remote priority on the bridge Mac: local-first (recommended) or always remote for a single audit trail?

**Technical, non-blocking:** payload size cap, lease duration/requeue policy, pairing-code TTL and role allowed to create bridges, backoff schedule, and whether enqueue is limited to test tickets first or all ticket types from day one.
